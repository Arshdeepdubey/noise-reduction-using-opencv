# Benchmark Report

Generated by `scripts/generate_test_data.py` + `scripts/benchmark.py`.
Re-run both to reproduce; all numbers below were produced by that exact
pipeline (see `results/benchmark_results.csv`, `results/benchmark_summary.csv`,
`results/video_benchmark.csv`) and are not hand-edited.

## 0. Methodology: what "clean" means here

Real low-light footage has no noise-free reference frame, so PSNR/SSIM
cannot be computed against it directly. This project instead takes
well-lit, effectively noise-free sample images (bundled with
scikit-image: astronaut, coffee, chelsea, camera), and:

1. synthetically **darkens** each one (`simulate_low_light`, exposure
   factor 0.15-0.35, gamma-correct-consistent), producing a
   **dark-but-still-noise-free reference**, then
2. adds a **signal-dependent Poisson (shot) + additive Gaussian (read)
   noise** model calibrated to that darkened image (`add_poisson_gaussian_noise`).

Every quality number below compares a denoiser's output against the
*dark reference from step 1*, not the original bright photo. This
matters: a denoiser is not expected to relight the scene (that is the
separate job of `low_light.enhance_low_light`, a CLAHE-based
post-process only used for visualization). Comparing against the
bright original would conflate "noise removed" with "scene relit" and
produce meaningless numbers — an early version of this benchmark made
exactly that mistake (see git history / project notes) and reported
PSNR values around 12-20 dB for *every* method, which barely
distinguished a denoiser from doing nothing. Fixing the reference to
the same-exposure dark image immediately separated the methods clearly
(noisy input ~20-24 dB vs. best denoisers ~28-32 dB).

Two noise levels are generated per image: `moderate` (exposure=0.35,
more shot noise, less read noise) and `severe` (exposure=0.15, less
shot noise in absolute terms but the scene itself is much darker, so
the effective SNR is worse) -- 8 image/level combinations in total.

## 1. Still-image benchmark (8 image x noise-level combinations)

Average over all 8 cases (`results/benchmark_summary.csv`):

| Method | PSNR (dB) | SSIM | Runtime (ms/image, 384x384-ish) |
|---|---:|---:|---:|
| **bilateral_optimized** | **31.44** | **0.783** | 12.3 |
| dct_denoise | 31.21 | 0.781 | 1310.0 |
| gaussian_baseline (trivial) | 30.97 | 0.727 | 0.3 |
| fuzzy_filter | 30.97 | 0.767 | 203.3 |
| bilateral_baseline (fixed params) | 30.60 | 0.713 | 11.4 |
| wavelet_visushrink | 27.21 | 0.549 | 21.8 |
| wavelet_bayesshrink | 26.37 | 0.523 | 22.8 |
| *noisy input (no denoising)* | *21.63* | *0.316* | *0* |

**Reading this table:**

- `bilateral_optimized` has the best average PSNR *and* SSIM of every
  method tested, while being (tied with the fixed-parameter baseline)
  the fastest non-trivial method — the combination the project brief
  asks for ("identify one method which gives better results ... measure
  quality & performance").
- `dct_denoise` is essentially tied on quality but **~110x slower**,
  which rules it out for the video/real-time part of the brief (see
  §3). This is a genuine, useful negative result, not a limitation of
  this implementation specifically — block-DCT thresholding with 50%
  block overlap is inherently expensive per pixel.
- `fuzzy_filter` needed a large similarity/gradient-threshold (its
  membership functions have to be wide relative to the ~20-30 sigma
  noise level actually present) to be competitive at all, and even
  then it is ~16x slower than bilateral per image, with the crucial
  extra cost coming from the O(window_area) neighbor loop.
- Wavelet shrinkage under-performed both bilateral and DCT here.
  Interestingly, **VisuShrink beat BayesShrink** on this test set
  (27.2 vs 26.4 dB) — the opposite of the general literature
  expectation (see `LITERATURE_SURVEY.md` §5) — which is consistent
  with BayesShrink's Gaussian-noise assumption being a worse fit to
  this project's *signal-dependent* Poisson-Gaussian low-light noise
  model than VisuShrink's simpler, more conservative threshold.
- The trivial `gaussian_baseline` (a single 5x5 Gaussian blur) is a
  reasonable PSNR performer but has visibly worse SSIM (0.727) than
  bilateral (0.783) or DCT (0.781) at similar-or-better speed — a
  concrete illustration of *why* edge-aware filtering matters: Gaussian
  blur removes noise indiscriminately and blurs edges/detail along
  with it, which PSNR (a purely pixelwise metric) under-penalizes but
  SSIM (which models structural/edge similarity) penalizes correctly.

## 2. Noise-adaptive bilateral filter: does the "optimization" actually help?

`bilateral_optimized` auto-estimates each frame's noise level (a
wavelet-MAD estimator, `noise_reduction.low_light.estimate_noise_sigma`)
and derives `sigma_color` from it, instead of using one fixed value for
every scene. Validation against the known injected noise level:

| Case | Injected noise std (measured) | Estimated sigma | `sigma_color` used |
|---|---:|---:|---:|
| astronaut_moderate | 26.9 | 25.0 | 75.1 |
| astronaut_severe | 16.6 | 17.3 | 51.9 |
| coffee_moderate | 24.9 | 25.3 | 76.0 |
| coffee_severe | 15.7 | 17.9 | 53.7 |
| camera_moderate | 28.5 | 29.3 | 88.0 |

The estimator tracks the true injected noise standard deviation to
within ~2 (0-255 scale) across every case, with no per-image or
per-noise-level manual tuning. Practically, this means one function
call handles both the `moderate` and `severe` noise regimes
automatically:

| Case | Fixed-default bilateral (`d=9, sigma=75,75`) | Auto-tuned optimized |
|---|---:|---:|
| astronaut_moderate | 26.79 dB | **28.48 dB** |
| astronaut_severe | **32.62 dB** | 31.68 dB |
| coffee_moderate | 28.05 dB | **29.27 dB** |
| coffee_severe | **33.35 dB** | 32.47 dB |
| camera_moderate | 26.71 dB | **29.32 dB** |

Honest reading: auto-tuning wins clearly on `moderate` noise (where the
fixed default under-smooths) and is within ~1 dB of a fixed default
that happens to suit `severe` noise well. The real-world value is not
"always wins by a large margin" but "one configuration performs
reasonably across a noise-level range a hand-picked fixed configuration
does not span" — relevant because actual low-light video noise varies
continuously with scene illumination and ISO, not in two discrete
buckets.

## 3. Continuous video benchmark

Synthetic 40-frame, 480x320, 20 fps low-light clip with small
per-frame camera jitter (`data/video/low_light_noisy.mp4`), quality
measured against the matching noise-free-but-dark reference frames.

| Method | Temporal filter | FPS | Avg PSNR (dB) | Avg SSIM |
|---|---|---:|---:|---:|
| bilateral_baseline | off | 70.5 | 30.18 | 0.826 |
| bilateral_baseline | on | 51.1 | 29.83 | 0.846 |
| **bilateral_optimized** | off | **69.2** | 30.11 | 0.839 |
| bilateral_optimized | on | 51.4 | 29.61 | **0.847** |
| wavelet_bayesshrink | off | 38.5 | 26.99 | 0.646 |
| wavelet_bayesshrink | on | 30.9 | 27.83 | 0.688 |
| fuzzy_filter | off (8-frame sample only) | 3.9 | 28.88 | 0.827 |
| dct_denoise | off (8-frame sample only) | 0.6 | 30.35 | 0.840 |

**Real-time viability**: both bilateral variants sustain **~50-70 fps**
in pure Python + stock OpenCV at 480x320 -- comfortably real-time
(>30 fps) even before the C++/NDK port discussed in
`ANDROID_PORTING.md`. `fuzzy_filter` and `dct_denoise` were only run on
an 8-frame sample specifically *because* their still-image runtimes
already rule them out for continuous video (0.6-3.9 fps); this is
reported directly as a benchmark finding, not silently omitted.

**Temporal filtering trade-off**: enabling the motion-adaptive temporal
EMA filter (`video_pipeline.TemporalDenoiser`) costs roughly 30% FPS
(extra per-frame blending work) and, perhaps surprisingly, *slightly
lowers* average per-frame PSNR for the bilateral methods (30.11 -> 29.61
for `bilateral_optimized`) while *raising* SSIM (0.839 -> 0.847). A
direct temporal-flicker measurement (mean absolute frame-to-frame pixel
difference across the output sequence) clarifies why:

| Sequence | Frame-to-frame difference (lower = more stable) |
|---|---:|
| noisy input (no denoising) | 17.24 |
| bilateral_optimized, spatial-only | 7.66 |
| bilateral_optimized, + temporal | 5.63 |
| bilateral_baseline, spatial-only | 8.28 |
| bilateral_baseline, + temporal | 6.13 |
| ideal noise-free reference sequence (has real camera-jitter motion) | 8.35 |

Temporal filtering measurably reduces flicker/shimmer (a major
perceptual complaint in real low-light video) beyond what spatial
filtering alone achieves. But note the reference sequence's own
frame-to-frame difference (8.35) is *higher* than the temporally
filtered output (5.63) — because the reference has genuine jitter
motion in it that the simple exponential-moving-average temporal filter
partially smooths over (a `motion_threshold` of 25 intensity levels
does not fully separate "noise" from "this small camera jitter"),
which is the source of the modest PSNR cost above. This is a known,
inherent limitation of naive temporal-EMA filtering (as opposed to a
proper motion-compensated temporal filter using optical flow), called
out explicitly as future work in `ANDROID_PORTING.md` rather than
glossed over.

## 4. Speed/quality knob: multi-resolution bilateral filtering

`bilateral_optimized(..., downscale=N)` filters the luma channel at
`1/N` resolution and upsamples (Paris & Durand-style fast bilateral
approximation). Measured on a synthetic 1280x720 frame:

| `downscale` | Time (best of 3) | Effective FPS | PSNR | SSIM |
|---:|---:|---:|---:|---:|
| 1 (off) | 40.6 ms | 24.6 | **33.12** | **0.810** |
| 2 | 32.5 ms | 30.8 | 30.11 | 0.752 |
| 4 | 32.1 ms | 31.2 | 26.77 | 0.680 |

This is a genuine, explicit trade-off (not a free lunch): `downscale=2`
buys ~25% more throughput for a real, visible quality cost, and
`downscale=4` gives almost no further speed benefit (fixed
per-frame overhead — noise estimation, color-space conversion, the two
cheap chroma passes — dominates once the luma pass itself is already
small) while quality keeps dropping. **Recommendation:** keep
`downscale=1` unless a specific device profile (see
`ANDROID_PORTING.md`) cannot otherwise sustain the target frame rate.

## 5. A concrete engineering pitfall worth recording

During development, `estimate_noise_sigma()` — which
`bilateral_optimized()` calls once per frame — was the dominant cost at
720p (~27-83 ms), *larger than the bilateral filter itself* (~12 ms),
because it ran a full-resolution wavelet transform on all three color
channels every call. Subsampling the input to at most 256 px per side
before the wavelet MAD estimate (`_ESTIMATION_MAX_DIM` in
`noise_reduction/low_light.py`) cut this to a small constant cost
independent of frame resolution, with the estimate changing by <2 (on
a 0-255 scale) versus the full-resolution computation. This is the kind
of profiling-driven fix that matters far more for real-time video than
micro-optimizing the filter kernel itself, and is a concrete example of
the "optimization steps taken" the project brief asks to be captured.
